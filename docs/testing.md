# Testing

Six vitest suites, colocated with their modules in `src/`: `curriculum.test.ts`, `dates.test.ts`, `demo.test.ts`, `stats.test.ts`, `store.test.ts`, `sync.test.ts`. There is no separate vitest config file — the `test: { environment: 'node' }` block lives in `vite.config.ts`. The environment is **node, not jsdom**: no DOM, no `localStorage`, no component rendering. Everything under test is a pure function or a fetch-injected async function; React components and screens have no tests (they are verified manually). Consequences of the node environment are load-bearing in two places: `store.test.ts` must stub `localStorage` itself, and `sync.test.ts` must inject a stubbed `fetch` (both `pullAll` and `pushAll` in `src/sync.ts` accept `f: typeof fetch = fetch` precisely for this).

## Running

```sh
npm test                         # vitest run — the whole suite, once
npx vitest run src/sync.test.ts  # one suite
npm test -- sync                 # same, by filename filter
npx vitest src/stats.test.ts     # one suite in watch mode
```

**Rule (see [operations.md](operations.md)): `npm test` AND `npm run build` must both be green before any commit.** The build runs `tsc --noEmit` first, so type errors are caught even where no test covers them; a green test run alone is not enough.

## Shared conventions

**Factory functions with a module-level `seq` counter.** `sync.test.ts` and `stats.test.ts` each define their own `mk` (Session) and `mkComp` (Competition) factories that increment a file-scoped `let seq = 0` per call. The counter serves two purposes: unique ids (`s${seq}`, `c${seq}`, `t${seq}`) so merge tests never accidentally collide, and — in `stats.test.ts`, where `createdAt: seq` — monotonically increasing creation times that the `historyFeed` tie-break tests depend on (a `mkComp` called after a `mk` has strictly larger `createdAt`; the "comp before session on createdAt tie" test then overrides `createdAt` explicitly). Signatures differ: sync's `mk(over: Partial<Session>)` fixes the date and takes overrides; stats' `mk(date, extra)` takes the date positionally because nearly every stats test varies it. Every factory emits a *complete* current-schema object (including `updatedAt` and `time: null`) — when a field is added to `Session`/`Competition` in `src/types.ts`, both factories must gain a default for it or dozens of tests fail on the round-trip/equality assertions.

**`appData(over)` over `emptyData()`.** `sync.test.ts` builds `AppData` fixtures as `{ ...emptyData(), ...over }` (importing `emptyData` from `src/store.ts`) rather than hand-writing the blob. This keeps fixtures automatically in sync with schema growth, and it also means the app_state push test asserts the pushed `state` equals `emptyData()`'s `focus`/`tagList`/`settings` — changing the defaults in `src/store.ts — emptyData` changes that test's expected payload.

**`stubFetch` / `okJson`.** `sync.test.ts` defines `stubFetch(respond)` returning `{ f, calls }`: `f` is a `typeof fetch` that records every `{ url, init }` into `calls` and returns `respond(url)`; `okJson(body)` builds a 200 JSON `Response`. Route-per-table behavior is expressed by branching on `url.includes('/sessions')` / `'/competitions'` inside `respond`. Tests then assert on `calls` — URL substrings, headers, and `JSON.parse(String(calls[0].init!.body))`.

**The localStorage stub.** `store.test.ts — stubStorage(raw)` installs a minimal `{ getItem: () => raw, setItem, removeItem }` on `globalThis` before each `load()` call and an `afterEach` deletes it. `src/store.ts — load` must therefore tolerate `localStorage` being a bare object, and any new persistence API used by `store.ts` must be added to this stub.

**`TODAY` pinned to `'2026-08-02'` (a Sunday).** Both `stats.test.ts` and `demo.test.ts` declare `const TODAY = '2026-08-02'` and every stats call passes it explicitly — no test ever lets "today" default to the wall clock. This is the point of the whole stats API design (see [stats.md](stats.md)): all stats are pure functions parameterized by `todayIso`, so tests are deterministic forever. Sunday is chosen deliberately: it exercises the `getDay() === 0` edge of Monday-start weeks (`mondayOf('2026-08-02') === '2026-07-27'`), gives a nearly complete current week for `weekSummary` bars, distinguishes "completed weeks" from "the open current week" in the streak-milestone tests, and pins day-of-year 214 for the year-pace projection math. The 30-day-window tests pin the exact boundary (`2026-07-04` in, `2026-07-03` out). If you ever change week-start or window semantics, these dates are where the change shows up first. `dates.test.ts` uses the same 2026 dates via `new Date(2026, 7, …)` local constructors — never `Date.parse` of an ISO string, which would be UTC (UTC APIs are banned for calendar dates; see [architecture.md](architecture.md)).

## What each suite pins

### `src/dates.test.ts`
Pure date helpers in `src/dates.ts`: local ISO round-trip (`toIso`/`parseIso`), `addDays` across month/year boundaries, `mondayOf` for Sunday/Monday/midweek inputs, display formats (`fmtToday`, `fmtShort`, `weekdayBadge`), `dayOfYear`, `autoTitle` (time-of-day plus weekend → "Open mat"), and the session-start-picker helpers: `fmtTime` 12-hour formatting including the hour-0 and noon edges (`00:15` → `12:15 AM`, `12:00` → `12:00 PM`), `toHhmm` zero-padding, and `resolveWhen` — the morning-after rule (null → now; a passed wall-clock time → today; a not-yet-passed time → *yesterday*; month boundaries crossed via day-overflow arithmetic).

### `src/store.test.ts`
`src/store.ts — load` migration/backfill behavior against raw localStorage blobs (via `stubStorage`). The fixture `session`/`comp` literals deliberately *omit* newer fields (`session` has no `updatedAt`, no `time`, no `competitions` sibling) to simulate pre-feature blobs. Pinned: `competitions` defaults to `[]` for old blobs and replaces junk values; stored competitions round-trip; `updatedAt` backfills from `createdAt` (pre-sync blobs); `time` backfills to `null` (pre-picker blobs) and round-trips when present; empty/unparseable storage yields `emptyData()`. **Every new persisted field needs a backfill test here** — old blobs in real browsers never disappear.

### `src/sync.test.ts`
The largest suite; covers `src/sync.ts` end to end. See [sync.md](sync.md) for the design these tests enforce.

- **Row mapping / sanitizer fuzzing** (`toRow`/`fromRow`, `toCompRow`/`fromCompRow`, `fromStateRow`). The fuzz style: build a known-good row via `toRow(mk())`, then spread in one tampered field at a time and assert the outcome is either *drop* (structural damage — bad id, bad date format, unparseable `updated_at` → `null`) or *fix* (recoverable damage — negative `rolls` → 0, non-whitelisted `round_min` → 5, non-array `tags` → `[]`, out-of-range `cardio` → 0, malformed `time` → `null`, matches jsonb junk filtered/clamped/capped at 50). Round-trips are asserted **ms-exact** (`fromRow(toRow(s))).toEqual(s)`) — timestamp precision loss would corrupt LWW. Remote is untrusted by design (anon key can insert/update), so **any new synced field needs both a round-trip case and tamper cases here**, matching the SQL check constraint (the triple declaration: `src/types.ts` union + `src/sync.ts` whitelist + `supabase-schema.sql` constraint must accept/reject identically).
- **Merge semantics** (`mergeSessions`, `mergeCompetitions`, `mergeAppData`, `isPushable`). The invariants: strictly-newer remote wins; ties and older remote keep local; remote-only rows are appended sorted by date-then-createdAt; **local rows missing remotely are never deleted**; `demo-` ids are ignored in both directions; and when nothing changed the merge returns **the same reference** (`toBe`, not `toEqual`) — this identity guarantee is what prevents pointless React re-renders after a no-op sync, and it is easy to silently break when refactoring `mergeById`. `mergeAppData` tests pin the `stateUpdatedAt` LWW clock (strictly-newer remote state adopted, older remote keeps local, `state: null` keeps local) and that pulled competitions are adopted in *both* state branches.
- **Push assertions** (`pushAll`). Each request is asserted by URL (`/rest/v1/sessions?on_conflict=id`, `/rest/v1/competitions?on_conflict=id`, `/rest/v1/app_state?on_conflict=user_id`), headers (`apikey` present, `Authorization: Bearer …`, `Prefer: resolution=merge-duplicates,return=minimal`), and parsed body (demo ids filtered out; app_state body carries `user_id: 'dmitrii'`). **Call-count coupling trap:** `pushAll` issues up to three requests, each conditional — sessions only if a non-demo session exists, competitions only if a non-demo comp exists, app_state only if `stateUpdatedAt > 0` — and the tests assert `calls` length and index (`calls[0]`) under fixtures crafted so exactly one request fires. When the competitions table was added, every existing `pushAll` expectation had to be re-audited because a comp in the fixture changes the expected length and shifts indices. **If you add another pushed table or make an existing push unconditional, re-derive every `toHaveLength`/`calls[n]` in this suite.** Also pinned: the competitions request tolerates a 404 (table not yet created — comps stay local) but any other status rejects; a non-ok sessions response rejects with the status in the message.
- **Pull assertions** (`pullAll`). URLs pinned including query string (`select=*&user_id=eq.dmitrii&order=updated_at.desc` for both tables); junk rows interleaved with good ones are dropped by the mappers; competitions 404 tolerated / other errors reject; empty app_state table → `state: null`.

### `src/stats.test.ts`
Every stats function in `src/stats.ts` except `tagCounts30d` and the `milestones` wrapper (those are exercised only via `demo.test.ts`), always with explicit `TODAY`. Pinned semantics: Monday–Sunday `weekSummary` with per-day bars and minutes from `rolls × roundMin`; `streak` counts a qualifying current week but never breaks on an unfinished one, and stops at the first under-goal completed week; the 30-day window is `[today-29, today]` inclusive; `volume12w` buckets oldest-first with the current week last; `yearTotals` is calendar-year only; milestone crossing dates, the completed-weeks-only rule for the 10-week streak milestone (9 completed + a qualifying open week is *not* achieved), and the year-pace projection month. Also `withSessionTags` (appends session-borne tags, same-reference when nothing is missing — another identity guarantee), `historyFeed` (sessions and competitions interleaved date-desc, `createdAt` tie-break, comp-first on exact ties — competitions enter stats *only* here, as history; every aggregate function takes `Session[]` so comps cannot affect streak/hours/rounds, see [stats.md](stats.md)), and `sortByDateDesc`.

### `src/demo.test.ts`
Runs `src/demo.ts — demoData(TODAY)` **through the real stats functions** to pin the numbers promised by the design handoff: current week 18 rolls / 3 sessions / bars `[4,0,8,0,6,0,0]`; 11-week streak since `2026-05-18`; 9 subs for / 12 against over 30 days; focus tagged in 7 of 11 sessions (64%); technique ranking with the focus tag on top; the exact 12-week volume series `[12,15,10,18,14,9,16,20,13,17,15,18]`; the milestone trio (quarter achieved, 10-week streak "Hit Jul 27", 500-rounds on pace). Assertions are exact where the seed is deterministic relative to `TODAY` and regex-tolerant (`/^Hit (May|Jun)/`) where a seed date floats with the quarter. Also pinned: no future or prior-year sessions, and the two demo competitions whose ids start with `demo-` (which is what keeps them from ever syncing — cross-checked by `isPushable` and the merge tests in `sync.test.ts`). **Editing the demo seed means re-deriving these numbers; editing stats semantics usually breaks this suite too, which is intentional — it is an integration test of seed × stats.**

### `src/curriculum.test.ts`
`src/curriculum.ts` ordering (see [curriculum.md](curriculum.md)): the real 2026-08 synced tag list (`REAL_TAGS`, in input/added order) maps to the exact GB-position-theme ordering; unknown tags land last in input order; matching is case-insensitive and trims while *output preserves the caller's spelling*; relative order within a group is stable; `groupTagsByCurriculum` emits only non-empty groups with labels; `CURRICULUM_GROUPS` ids stay in the canonical sequence `standing, guard, passing, side, mount, back, legs, other`. The judgment-call deviations are pinned as named tests so they read as documentation: `Escapes` → side control, `Half guard` → guard, `Darce` → back. Finally, every entry of `src/store.ts — DEFAULT_TAGS` must map to a real group, never `other` — **adding a default tag requires a curriculum mapping first.**

## When you change X, update these tests

| Change | Update |
| --- | --- |
| Add/rename a `Session` or `Competition` field (`src/types.ts`) | `mk`/`mkComp` defaults in `sync.test.ts` *and* `stats.test.ts`; round-trip + tamper cases in `sync.test.ts`; backfill case in `store.test.ts`; SQL addendum in `supabase-schema.sql` (see [data-model.md](data-model.md)) |
| Whitelisted value set (`RoundMin`, `CardioRating`, time regex) | sanitize cases in `sync.test.ts` — and the TS union + SQL check constraint must change in lockstep (triple declaration) |
| `emptyData()` defaults (`src/store.ts`) | `pushAll` app_state body assertion and `fromStateRow` fallback assertions in `sync.test.ts` |
| `load()` migrations (`src/store.ts`) | `store.test.ts` (add a pre-migration-blob case) |
| Add/remove/uncondition a `pushAll` request | every `calls.toHaveLength` / `calls[n]` in `sync.test.ts — pushAll` (the call-count trap above), plus the demo-only "sends nothing" cases |
| Pull URL shape (select/filter/order) | URL substring assertions in `sync.test.ts — pullAll` |
| Merge/LWW semantics (`mergeById`, `mergeAppData`) | `sync.test.ts` merge suites — keep the same-reference (`toBe`) cases passing |
| Week start, window sizes, milestone thresholds, pace math (`src/stats.ts`) | `stats.test.ts` boundary dates *and* `demo.test.ts` pinned numbers |
| Demo seed (`src/demo.ts`) | `demo.test.ts` — re-derive every pinned number by running the seed through stats |
| Curriculum groups or tag mappings (`src/curriculum.ts`) | `curriculum.test.ts` incl. the `REAL_TAGS` expected ordering |
| `DEFAULT_TAGS` (`src/store.ts`) | `curriculum.test.ts` "never other" loop |
| Date helpers (`src/dates.ts`) | `dates.test.ts`; downstream `stats.test.ts` boundaries if week/window math shifts |

## Gaps (known, accepted)

No component/DOM tests (node environment, jsdom not installed), no service-worker tests (`public/sw.js` + `scripts/sw-precache.mjs` are verified by `npm run build` and manual deploys — see [build-pwa.md](build-pwa.md)), no tests against a real Supabase instance (the PostgREST contract is pinned only via the stubbed URL/header/body assertions — see [sync.md](sync.md)).
